## 4. Subsurface structures

Two structural axes, both with strong literature precedent:

- **Axis A** — Subsurface architecture and surface-runoff handling, **3 levels** [LOCKED]:
  1. **HBV-style with single linear FAST_RES release** (S1, S2) — current production baseline
  2. **HBV-style with Q0+Q1 threshold release** (S3, S4) — Bergström 1976 / HBV-Light Q0 mechanism on FAST_RES
  3. **SPHY-faithful** (S5, S6) — direct overland routing on land HRUs + cascade percolation TOPSOIL→FAST→SLOW (no flush of sat-excess to FAST_RES); Terink 2015 architecture
- **Axis B** — Glacier–groundwater connectivity, **2 levels** [LOCKED]: off (no `:Split`) vs on (`:Split` with GlacROF on MASKED_GLACIER HRUs)

This gives a **3×2 factorial with 6 structures**: S1, S2, S3, S4, S5, S6. All locked below.

### 4.1 S1 — Baseline: 2-reservoir HBV-style architecture with linear outflow [LOCKED]

**Conceptual description.** Two-reservoir subsurface (FAST_RES + SLOW_RES), both with linear baseflow release. Saturation-excess on land HRUs is generated by the HBV β-power infiltration partition but is then *immediately routed into FAST_RES via `:Flush`* — there is **no direct overland flow pathway from soil-covered HRUs to the outlet**. Glacier meltwater enters via IRRIGATION on MASKED_GLACIER HRUs; because TOPSOIL is impermeable on those HRUs, the meltwater is forced to SURFACE_WATER and routed directly to the outlet (no glacier→GW pathway). This is the current production baseline used in the in-flight calibration runs.

**Configuration in codebase.**
- Configuration layer: `src/config/layers/configurations/glogem_subdaily_opt1.yaml`
- Subsurface structure: `gw_2_layer` (FAST_RES + SLOW_RES)
- Glacier routing: `none` (no `:Split` process)
- Percolation algorithm: `PERC_CONSTANT` FAST_RES → SLOW_RES (perc_option=1)
- Baseflow on both reservoirs: `BASE_LINEAR`

**Process layout (key lines):**
```
:Infiltration   INF_HBV         PONDED_WATER → MULTIPLE        # β-power sat-excess partition
:Flush          RAVEN_DEFAULT   SURFACE_WATER → FAST_RESERVOIR # land HRUs only:
                                                                #   IS_NOT GLACIER/MASKED_GLACIER/ROCK/LAKE
:Percolation    PERC_CONSTANT   FAST_RES → SLOW_RES
:Baseflow       BASE_LINEAR     FAST_RES → SURFACE_WATER
:Baseflow       BASE_LINEAR     SLOW_RES → SURFACE_WATER
```

**Glacier meltwater path (S1):**
1. GloGEM-derived melt arrives as IRRIGATION → PONDED_WATER on MASKED_GLACIER HRUs each timestep
2. MASKED_GLACIER HRUs have IMPERM=1.0, so `:Infiltration INF_HBV` cannot partition water to TOPSOIL
3. All meltwater → SURFACE_WATER
4. The `:Flush SURFACE_WATER → FAST_RES` step is conditioned on `IS_NOT MASKED_GLACIER`, so glacier SURFACE_WATER is NOT flushed
5. SURFACE_WATER routes directly to catchment outlet via `:CatchmentRoute TRIANGULAR_UH`
6. **Net effect: 100% of glacier meltwater becomes immediate surface runoff to outlet. There is no path for glacier melt to ever enter the slow baseflow pool.**

**Land-HRU surface-runoff path (S1):**
1. Rainfall + snowmelt → PONDED_WATER
2. `:Infiltration INF_HBV` partitions PONDED_WATER between TOPSOIL (the infiltration fraction) and SURFACE_WATER (the saturation-excess fraction). Partition controlled by HBV_BETA and current TOPSOIL saturation state.
3. `:Flush SURFACE_WATER → FAST_RESERVOIR` on land HRUs immediately moves sat-excess overland flow into FAST_RES (no direct path to outlet)
4. FAST_RES drains via `:Baseflow BASE_LINEAR` to SURFACE_WATER (single linear time constant), then through routing to outlet
5. FAST_RES also percolates downward to SLOW_RES via `:Percolation PERC_CONSTANT`
6. SLOW_RES drains via `:Baseflow BASE_LINEAR` to SURFACE_WATER (slower linear time constant)
7. **Net effect: all land-HRU surface runoff (sat-excess overland) and shallow subsurface response are lumped into the single linear FAST_RES storage.** The model cannot distinguish overland flow from shallow interflow.

**Calibrated parameters (SPHY perc_option=1 set, 12 total):**
X01 (RainSnow_Temp), X02 (Melt_Factor), X03 (CFR), X04 (Snow_SWI), X05 (HBV_Beta), X06 (Field_Capacity), X07 (Baseflow_Coeff_Fast), X08 (Baseflow_Coeff_Slow), X09 (T_Conc), X10 (Thickness_Topsoil), X11 (Max_Perc_Rate_Fast), X15 (Max_Cap_Rise_Rate). Precipitation correction in SPHY is handled via HBVEC_LAPSE in the .rvp (not a calibrated X-numbered parameter).

**Hypothesis tested by S1.** None directly — S1 is the reference against which the other structures are compared. As the current production baseline, it represents the "do-nothing" structural choice.

### 4.2 S2 — S1 + glacier–groundwater connectivity [LOCKED]

**Conceptual description.** Identical to S1 in every respect *except* the glacier meltwater path. Glacier melt is no longer routed entirely to SURFACE_WATER; instead a fraction GlacROF goes to SURFACE_WATER (immediate runoff) and (1−GlacROF) is routed to SLOW_RES, where it joins the slow-baseflow pool. This introduces a structurally explicit glacier → groundwater pathway. The mechanism follows the SPHY-style `:Split` process used by Terink et al. 2015 and adopted in our `glacier_gw_*` configurations.

**Configuration in codebase.**
- Base configuration layer: `glogem_subdaily_opt1.yaml` (same as S1)
- **Override**: set `glacier_routing: 'split_to_slow'` (currently supported by `preprocess_SPHY.py` line ~1566 — `:Split` process inserted before `:Infiltration` on MASKED_GLACIER HRUs)
- Subsurface structure: `gw_2_layer` (same as S1)
- Percolation algorithm: `PERC_CONSTANT` FAST_RES → SLOW_RES (same as S1)
- Baseflow on both reservoirs: `BASE_LINEAR` (same as S1)

**Implementation TODO.** Need to either (a) create a new SPHY-compatible configuration layer file (e.g., `glogem_subdaily_opt1_glacier_gw.yaml`) that inherits from `glogem_subdaily_opt1` and sets `glacier_routing: 'split_to_slow'`, or (b) update the existing `glacier_gw_2layer_glogem.yaml` config to be SPHY-compatible (currently `compatible_models: [HBV]`). Path (a) is cleaner; path (b) consolidates existing variants.

**Process layout (only the difference vs S1):**
```
# Inserted BEFORE :Infiltration:
:Split          RAVEN_DEFAULT   PONDED_WATER → SURFACE_WATER + SLOW_RESERVOIR   GlacROF
   :--> Conditional HRU_TYPE IS MASKED_GLACIER
```

All other processes (`:Infiltration`, `:Flush`, `:Percolation`, `:Baseflow`) identical to S1.

**Glacier meltwater path (S2):**
1. GloGEM melt arrives as IRRIGATION → PONDED_WATER on MASKED_GLACIER HRUs
2. `:Split` partitions PONDED_WATER: GlacROF · PONDED → SURFACE_WATER, and (1−GlacROF) · PONDED → SLOW_RES
3. The SURFACE_WATER fraction (immediate runoff) routes directly to outlet
4. The SLOW_RES fraction joins the slow groundwater pool; it later drains via `:Baseflow BASE_LINEAR` with the same coefficient as land-derived SLOW_RES baseflow
5. **Net effect: glacier melt now has a path into the slow baseflow pool. The model can represent glacier-derived baseflow.**

**Land-HRU paths identical to S1** — land-HRU surface runoff still flushes to FAST_RES; no architectural change for non-glacier HRUs.

**Calibrated parameters (S2 set).** Same 13 parameters as S1, plus X16 (GlacROF) becomes a calibrated parameter (previously implicit in glacier-melt-to-surface routing). X16 ∈ [0, 1].

**Hypothesis tested by S2 vs S1.** "Glacier meltwater partly enters slow groundwater storage rather than reaching the stream as immediate surface runoff." Direct test of the Hayashi 2020 / Somers 2020 / Cochand 2019 / van Tiel 2024 framing of mountain glacier–groundwater connectivity.

**Note on parameter limits.** With GlacROF = 1.0, S2 reduces exactly to S1 (all meltwater to surface). With GlacROF = 0.0, all glacier melt enters SLOW_RES. The calibration is free to find any intermediate value. If the calibrated GlacROF approaches 1.0 in a catchment, that catchment's calibration is implicitly saying "glacier-GW connectivity is not needed to explain observations here."

### 4.3 S3 — S1 + threshold release from FAST_RES [LOCKED]

**Conceptual description.** Identical to S1 in architecture (lumped sat-excess flushed to FAST_RES, no glacier-GW pathway, single PERC_CONSTANT, linear SLOW_RES outflow), with one change: FAST_RES now has *two* concurrent baseflow release mechanisms instead of one — a threshold-driven "fast burst" Q0 that activates only when FAST_RES storage exceeds UZL, plus the linear background Q1 that is always active. This is the HBV-Light convention (Bergström 1976; Seibert & Vis 2012) for separating quick stormflow-like response from sustained shallow-baseflow drainage within the upper reservoir.

S3 tests whether the lumping concern with S1's single-linear FAST_RES — that one linear coefficient cannot simultaneously represent (i) true overland-flow-like rapid response and (ii) sustained shallow interflow — actually matters for baseflow representation in glacierized catchments. The structural alternative is well-precedented (HBV-Light is a workhorse mountain-hydrology model) and Stölzle et al. 2014 explicitly identifies "threshold or parallel structures" as the most successful for baseflow modeling.

**Configuration in codebase.**
- Base configuration layer: `glogem_subdaily_opt1.yaml` (same as S1) **plus a new flag**: `fast_reservoir_release: 'threshold'` (default for S1/S2: `'linear'`).
- Subsurface structure: `gw_2_layer` (same as S1)
- Glacier routing: `none` (no `:Split` — same as S1)
- Percolation algorithm: `PERC_CONSTANT` FAST_RES → SLOW_RES (same as S1)
- **DIFFERENCE vs S1**: FAST_RES emits TWO `:Baseflow` processes instead of one — a threshold-power release for Q0 plus the linear release for Q1. SLOW_RES outflow remains `BASE_LINEAR` (unchanged).

**Implementation TODO.** New variant in this codebase. Requires:
1. Add `fast_reservoir_release: 'linear' | 'threshold'` config flag handling in `preprocess_SPHY.py`
2. When `threshold`: emit a Raven `:Baseflow BASE_THRESH_POWER FAST_RESERVOIR → SURFACE_WATER` line (or `BASE_THRESH_LINEAR` if available — needs verification of Raven's exact process names) in addition to the existing `:Baseflow BASE_LINEAR FAST_RESERVOIR → SURFACE_WATER`. Verify which Raven baseflow algorithm gives `Q = K0·MAX(0, S − UZL)^n` (with n=1 reducing to the HBV-Light Q0 form).
3. Add parameter columns for UZL and K0 to the FAST_RES row of the SPHY soil parameter table in `_build_soil_class_parameters()`.
4. Define X-numbers, init values, and lower/upper bounds for UZL and K0 in `src/config/default_params.yaml` (SPHY section). Suggested numbering: X17 (UZL), X18 (K0). Bounds from HBV-Light literature: UZL ≈ [5, 50] mm; K0 ≈ [0.1, 0.5] /day (when interpreted as a linear coefficient on `S − UZL`).
5. Update calibration namelists to include X17/X18 in the calibrated parameter set when `fast_reservoir_release: 'threshold'`.

**Process layout (only the difference vs S1):**
```
# Replaces the single :Baseflow BASE_LINEAR FAST_RES → SURFACE_WATER line:
:Baseflow       BASE_THRESH_POWER   FAST_RES → SURFACE_WATER   # Q0: fires only when S_fast > UZL
:Baseflow       BASE_LINEAR         FAST_RES → SURFACE_WATER   # Q1: always-on linear background
# SLOW_RES baseflow unchanged from S1
```

All other processes (`:Infiltration`, `:Flush`, `:Percolation`) identical to S1.

**Calibrated parameters (S3 set).** Same 12 parameters as S1 (X01–X11, X15) plus:
- **X17 (UZL)**: threshold storage above which Q0 activates [mm]. Range [5, 50].
- **X18 (K0)**: above-threshold release rate [1/day]. Range [0.1, 0.5].

Total: 14 calibrated parameters in S3 (vs 12 in S1).

**Glacier meltwater path (S3).** Identical to S1 — glacier melt routes 100% to SURFACE_WATER and on to outlet via routing. No glacier-GW pathway. S3's only difference from S1 is the FAST_RES release mechanism on land HRUs.

**Land-HRU surface-runoff path (S3):**
1. Rainfall + snowmelt → PONDED_WATER (same as S1)
2. `:Infiltration INF_HBV` β-power partition (same as S1)
3. `:Flush SURFACE_WATER → FAST_RESERVOIR` (same as S1 — saturation-excess overland still lumped into FAST_RES)
4. FAST_RES drains via TWO concurrent mechanisms:
   - `:Baseflow BASE_THRESH_POWER`: Q0 = K0 · MAX(0, S_fast − UZL) — activates only when FAST_RES storage exceeds threshold UZL. Captures "fast burst" response to large recharge events.
   - `:Baseflow BASE_LINEAR`: Q1 = K1 · S_fast (where K1 is the existing X07 BASEFLOW_COEFF). Always-on background drainage. Captures sustained shallow interflow.
5. FAST_RES → SLOW_RES via `:Percolation PERC_CONSTANT` (same as S1)
6. SLOW_RES → SURFACE_WATER via `:Baseflow BASE_LINEAR` (same as S1)

**Hypothesis tested by S3 vs S1.** "The fast reservoir requires two distinct release mechanisms — a threshold-activated quick response and a linear background — to adequately represent the range of catchment fast-flow behaviors observed in glacierized mountain catchments." If S3 outperforms S1 on baseflow (KGE_winter) without degrading Q-KGE, the threshold mechanism is justified structurally. If S3 doesn't improve over S1, the single-linear FAST_RES is sufficient and the added parameters are unnecessary.

### 4.4 S4 — S3 + glacier–groundwater connectivity [LOCKED]

**Conceptual description.** Stacks both structural changes from S2 and S3. Identical to S1 except:
- FAST_RES has Q0+Q1 release mechanism (same as S3)
- Glacier meltwater partitioned via `:Split` with GlacROF (same as S2)

Allows direct test of additivity vs interaction between the two structural changes: does combining threshold-FAST and glacier-GW give more (or less) improvement than the sum of either change alone?

**Configuration in codebase.**
- Base configuration layer: `glogem_subdaily_opt1.yaml`
- Set `fast_reservoir_release: 'threshold'` AND `glacier_routing: 'split_to_slow'`
- Subsurface structure: `gw_2_layer`
- Percolation algorithm: `PERC_CONSTANT` (same as S1/S2/S3)

**Implementation TODO.** Builds on the implementation work for S2 (glacier-GW config) and S3 (threshold release). Once both are implemented independently, S4 is the union of both flags on the baseline config. Single new config file (or namelist override).

**Process layout (differences vs S1).** Combines the additions in S2 and S3:
```
# Inserted BEFORE :Infiltration (from S2):
:Split          RAVEN_DEFAULT       PONDED_WATER → SURFACE_WATER + SLOW_RESERVOIR   GlacROF
   :--> Conditional HRU_TYPE IS MASKED_GLACIER

# Replaces single :Baseflow BASE_LINEAR FAST_RES → SURFACE_WATER (from S3):
:Baseflow       BASE_THRESH_POWER   FAST_RES → SURFACE_WATER   # Q0
:Baseflow       BASE_LINEAR         FAST_RES → SURFACE_WATER   # Q1
```

**Calibrated parameters (S4 set).** 16 parameters: the 13 from S1, plus X16 (GlacROF, from S2), plus X17 (UZL) and X18 (K0) (from S3).

**Glacier meltwater path (S4).** Identical to S2 — partitioned by `:Split` with GlacROF, (1−GlacROF) fraction to SLOW_RES contributing to slow baseflow.

**Land-HRU surface-runoff path (S4).** Identical to S3 — sat-excess flushed to FAST_RES which has Q0+Q1 release.

**Hypothesis tested by S4.** "The two structural changes are additive" (i.e., the gain S4 over S1 ≈ gain S2 over S1 + gain S3 over S1). If S4 substantially exceeds the sum of the individual improvements, the changes interact (the threshold-FAST mechanism reveals more baseflow signal *because of* the glacier-GW pathway, or vice versa). If S4 does not exceed the sum, the two are independent and the simplest of {S2, S3} that gives most of the improvement is preferred by parsimony.

### 4.5 S5 — SPHY-faithful architecture (direct overland + cascade percolation), no glacier-GW [LOCKED]

**Conceptual description.** A genuinely SPHY-faithful structure in the Terink 2015 sense: saturation-excess generated on land HRUs is **not** routed into FAST_RES; instead it goes directly to SURFACE_WATER and on to the outlet via `:CatchmentRoute TRIANGULAR_UH`. FAST_RES is therefore not a surface-flow buffer — it is a genuine subsurface reservoir, fed from above by percolation from TOPSOIL via a two-stage cascade (PERC_POWER_LAW: TOPSOIL → FAST_RES; PERC_LINEAR: FAST_RES → SLOW_RES). Both reservoir outflows remain linear (`BASE_LINEAR`). Glacier meltwater path is identical to S1 (100% to SURFACE_WATER → outlet, no glacier-GW).

S5 tests whether the architectural choice itself — separating overland surface flow from subsurface reservoir storage — matters for baseflow representation, independent of any change to FAST_RES release dynamics. This is the closest the design comes to Terink-SPHY's actual architecture (still simplified relative to the real SPHY routing module, but architecturally distinct from the HBV-style flush-to-FAST setup).

**Configuration in codebase.**
- Base configuration layer: needs a new file (e.g., `glogem_subdaily_opt2_direct.yaml`) that sets `perc_option: 2` AND a new flag `land_surface_routing: 'direct'`.
- Subsurface structure: `gw_2_layer` (FAST_RES + SLOW_RES, same as S1)
- Glacier routing: `none` (no `:Split` — same as S1)
- Percolation algorithm: cascade — `PERC_POWER_LAW` TOPSOIL → FAST_RES + `PERC_LINEAR` FAST_RES → SLOW_RES (perc_option=2)
- Baseflow on both reservoirs: `BASE_LINEAR` (same as S1)
- **DIFFERENCE vs S1**: no `:Flush SURFACE_WATER → FAST_RESERVOIR` on land HRUs (sat-excess routes directly to outlet); two-stage cascade percolation instead of single PERC_CONSTANT.

**Implementation TODO.** New variant in this codebase. Requires:
1. Add `land_surface_routing: 'flush_to_fast' | 'direct'` config flag handling in `preprocess_SPHY.py`.
2. When `direct`: drop the `:Flush SURFACE_WATER → FAST_RESERVOIR` block from the HydrologicProcesses emission entirely (or change the conditional set so it excludes all HRU types — equivalent to not emitting the line).
3. The cascade percolation (perc_option=2) is already supported in `preprocess_SPHY.py` (`percolation_block` branches on `perc_option`); just needs to be selected in the config.
4. Both opt2 and direct routing must be set together (otherwise we get the incoherent intermediate: opt2 cascade AND flush-to-FAST, which is what the previous opt2 actually was). Add a config-level assertion or use a single `architecture: 'sphy_faithful'` umbrella flag.

**Process layout (differences vs S1):**
```
# REMOVED (compared to S1): the :Flush SURFACE_WATER → FAST_RESERVOIR block
# (Sat-excess SURFACE_WATER on land HRUs routes directly to outlet via :CatchmentRoute)

# REPLACED (perc_option=1 → perc_option=2): single PERC_CONSTANT replaced with cascade
:Percolation    PERC_POWER_LAW   TOPSOIL → FAST_RES           # X12, X13
:Percolation    PERC_LINEAR      FAST_RES → SLOW_RES          # X14

# UNCHANGED from S1:
:Infiltration   INF_HBV          PONDED_WATER → MULTIPLE      # β-power sat-excess partition
:Baseflow       BASE_LINEAR      FAST_RES → SURFACE_WATER
:Baseflow       BASE_LINEAR      SLOW_RES → SURFACE_WATER
```

**Calibrated parameters (S5 set).** 14 parameters: 11 shared with S1 (X01–X10, X15) PLUS three perc_option=2 parameters (X12 Max_Perc_Rate_Topsoil, X13 Perc_N, X14 Perc_Coeff) instead of S1's single X11. Bounds for X12/X13/X14 already defined in `src/config/default_params.yaml`.

Compared to S1: replace `{X11}` with `{X12, X13, X14}` — net +2 parameters (12 → 14).

**Glacier meltwater path (S5).** Identical to S1 — IRRIGATION arrives on MASKED_GLACIER, IMPERM=1.0 blocks infiltration, all meltwater → SURFACE_WATER → outlet. No glacier-GW pathway.

**Land-HRU surface-runoff path (S5):**
1. Rainfall + snowmelt → PONDED_WATER (same as S1)
2. `:Infiltration INF_HBV` β-power partition: PONDED → TOPSOIL (infiltrated fraction) + SURFACE_WATER (saturation-excess overland fraction). Same partition mechanism as S1.
3. **No `:Flush`** — SURFACE_WATER from saturation excess is NOT moved to FAST_RES. It stays in SURFACE_WATER and routes directly to outlet via `:CatchmentRoute TRIANGULAR_UH`.
4. TOPSOIL → FAST_RES via `:Percolation PERC_POWER_LAW` (rate set by X12, exponent X13). This is now the *only* source of water for FAST_RES on land HRUs.
5. FAST_RES → SLOW_RES via `:Percolation PERC_LINEAR` (coefficient X14)
6. FAST_RES → SURFACE_WATER via `:Baseflow BASE_LINEAR` (coefficient X07)
7. SLOW_RES → SURFACE_WATER via `:Baseflow BASE_LINEAR` (coefficient X08)
8. **Net effect**: land-HRU "fast" response is now two physically distinct pathways: (a) immediate overland flow from SURFACE_WATER directly to outlet via routing; (b) shallow subsurface flow from FAST_RES (fed by percolation from TOPSOIL) via BASE_LINEAR baseflow. The model can in principle distinguish these.

**Hypothesis tested by S5 vs S1.** "The architecture of routing sat-excess overland flow directly to the outlet (Terink SPHY style), rather than lumping it into the upper subsurface reservoir (HBV style), better represents the fast/slow water-source separation in glacierized mountain catchments." Tests architectural choice independent of the FAST_RES release-mechanism choice tested in S3.

**Comparison S3 vs S5 (different routes to addressing the same lumping concern).** Both S3 and S5 attempt to give the model more flexibility in representing fast-flow timing. S3 keeps the HBV architecture but adds a Q0 threshold release inside FAST_RES (more parameters in the same reservoir). S5 changes the architecture so that sat-excess bypasses FAST_RES entirely (no extra parameters in FAST_RES release, but additional percolation parameters for the new TOPSOIL→FAST stage). The paper can compare which approach is more effective — a small parametric refinement (S3) or an architectural restructuring (S5).

**Configuration in codebase.**

**Implementation TODO.** Builds on the implementation work for S5 (direct overland routing + cascade percolation) and S2 (`:Split` glacier-GW). No new mechanisms.

**Process layout (differences vs S1):** S5 changes (no flush, cascade percolation) AND S2 change (`:Split` glacier-GW). See §4.5 and §4.2 individually.

Comparison with S2 (which has glacier-GW but no architectural restructure) isolates this.

### 4.7 Summary table — the 9 structures (3×3 factorial) [REVISED 2026-06-01]

The original Paper 5 design (S1-S6) was a 3×2 factorial: architecture × {no glacier-GW, glacier→SLOW}. On 2026-06-01 we identified that the "glacier→SLOW" choice rests on weak literature support — Huang 2026 adopts it as a calibration choice rather than from established field evidence, and the glacier-hydrology textbook view (Fountain & Walder 1998; Hock 2005; Irvine-Fynn 2011) instead points toward fast (channelised) release. To turn this hidden assumption into a testable axis, the design is expanded to a 3×3 factorial with a third glacier-GW level — glacier→FAST — applied to all three architectures (S7/S8/S9 below).

| | **FAST_RES: linear, flush-to-FAST** | **FAST_RES: Q0 threshold + Q1 linear, flush-to-FAST** | **SPHY-faithful: cascade percolation, direct overland** |
|---|---|---|---|
| **Glacier → surface (no `:Split`)** | **S1** — 12 params | **S3** — 14 params (S1 + UZL, K0) | **S5** — 14 params (S1 − X11 + X12,X13,X14) |
| **Glacier → SLOW (`:Split` to SLOW_RES, GlacROF)** | **S2** — 13 params (S1 + GlacROF) | **S4** — 15 params (S3 + GlacROF) | **S6** — 15 params (S5 + GlacROF) |
| **Glacier → FAST (`:Split` to FAST_RES, GlacROF)** | **S7** — 13 params (S1 + GlacROF) | **S8** — 15 params (S3 + GlacROF) | **S9** — 15 params (S5 + GlacROF) |

## 12. Multi-objective selection rule & metric scaling (2026-06-01) [LOCKED]

This section captures decisions made during the analysis of the 3 finished Swiss Pareto runs (2268 Rhone, 2256 Rosegbach, 2161 Massa), which surfaced two methodological issues that needed resolving before Phase 1 expansion.

### 12.1 Issue: Pareto-front-derived min-max rescaling has a narrow-axis pathology

The original Path A from the multi-objective design discussion (paper_ideas/multiobj_calibration_literature.md and earlier sessions) was to use per-objective min/max from the Pareto front to rescale objectives before computing a Tchebycheff-distance compromise solution.

In practice, this **systematically biases the selection toward whichever axis has the narrowest Pareto-front range**:

- For catchment 2161 Massa: Q-KGE Pareto-front span = 0.039; baseflow-KGE Pareto-front span = 0.576 (15× wider)
- After min-max rescaling, a 0.01 absolute improvement in Q-KGE = 25% of the Q-rescaled axis, but a 0.01 improvement in baseflow = 1.7% of the baseflow-rescaled axis
- Tchebycheff then over-prefers Q-strong points at the cost of much larger baseflow degradations

Empirical demonstration on the 3 Swiss catchments:
| Catchment | Tcheb-pareto baseflow KGE | SCEUA weighted-sum baseflow KGE |
|---|---|---|
| 2256 | 0.672 | **0.909** |
| 2161 | 0.483 | **0.896** |

SCEUA weighted-sum found points on the Pareto front with much better baseflow — the Tchebycheff-pareto-range rule preferred narrow Q gains over substantial baseflow gains.

### 12.2 Decision: use theoretical-bounds rescaling for Tchebycheff selection [LOCKED]

For the paper's primary Pareto selection rule, rescale each objective using **fixed theoretical bounds**, not the data-derived Pareto range. The new `select_pareto_best.py --rescaling theoretical` mode implements:

- KGE-family metrics (KGE, KGE_NP, LogKGE, NSE, KGE_winter): clamp negatives at 0 → rescale by [0, 1]
- 1−RMSE on bounded variables (fSCA): assume already in [0, 1]
- Any rescaled value clamped to [0, 1] (no rewarding "better than ideal")

Re-running on the 3 Swiss Pareto fronts gave more balanced selections (2161 baseflow KGE went from 0.483 → 0.687). Theoretical bounds also enable **direct cross-catchment comparison** — the rescaling is the same regardless of which catchment is being analyzed.

### 12.3 Residual issue: snow score has a structural ceiling around 0.7

Even under theoretical-bounds Tchebycheff, the worst-shortfall axis in all 3 Swiss catchments is now **snow** — because `1 − RMSE` on fSCA has an empirical ceiling around 0.7 (data noise floor + bounded variable). The metric *cannot* reach 1.0 the way KGE on streamflow can.

This is an irreducible asymmetry of the (KGE on Q, 1−RMSE on snow, KGE on baseflow) objective family.

### 12.4 Decision: switch snow metric to nRMSE for Phase 1 onward [LOCKED]

For Phase 1 calibrations and all subsequent work, use **`nRMSE` (mean-normalized RMSE) for the snow objective** instead of `RMSE`:

```
nRMSE = 1 − RMSE / mean(obs)
```

Key properties:
- Natural [−∞, 1] range like KGE — no structural ceiling
- Weights errors by snow-signal magnitude per elevation band
- Already implemented in `src/calibration_objectives.py` (added 2026-05-29, with documentation and synthetic-data validation)

Effect: weighted-sum objective composition becomes cleaner without needing per-objective rescaling, and theoretical-bounds Tchebycheff stops having snow as the universal binding constraint.

### 12.5 Hunza Pareto (currently running, ~12% done as of 2026-06-01)

**Keeps `RMSE`** for snow (does not get re-launched). Justification: the 3.5-day compute commitment outweighs the metric-choice cleanliness gain. At analysis time when Hunza finishes, we can either:
- Apply theoretical-bounds Tchebycheff with the existing RMSE-on-snow front (snow will be limiting)
- Or compute nRMSE post-hoc from the stored snow time series and re-rank the front

### 12.6 Baseflow window: deep_winter (Dec-Jan-Feb) [LOCKED 2026-06-01]

Decision: Phase 1 calibrations use `window: 'deep_winter'` = months (12, 1, 2) — the 3-month meteorological deep winter (DJF). Reasons:

- **Reliably below freezing across all study catchments** regardless of regime (Swiss alpine, Pakistan UIB, Nepal high alpine). No need to defend per-catchment window choices.
- **Conservative**: avoids both shoulder-month risks (November autumn-melt at lower Swiss elevations; March early-spring melt in Pamir).
- **Statistical power adequate**: ~90 days/year × ~30 years calibration period = 2700 days of winter-baseflow data per catchment — far more than needed for a stable KGE.
- Compared to Huang et al. 2026's NDJF (Nov-Feb), we exclude November to avoid Swiss autumn-melt contamination, accept losing 1 month of Pakistan winter (negligible impact given the long cold winter there).

Window presets now defined in `src/calibration_objectives.py::_resolve_window`:
- `'winter'`       → NDJFM (11, 12, 1, 2, 3) — 5 months
- `'raw_winter'`   → DJFM (12, 1, 2, 3) — 4 months, **legacy Hunza pilot value**
- **`'deep_winter'` → DJF (12, 1, 2) — 3 months — Phase 1 LOCKED CHOICE**
- `'huang_winter'` → NDJF (11, 12, 1, 2) — 4 months, matches Huang 2026 exactly

**Hunza Pareto (running)** uses `raw_winter` = DJFM by design (launched before this decision). Phase 1 namelists going forward will use `deep_winter`.

### 12.8 Calibration metrics per objective [LOCKED 2026-06-01]

After reviewing Cinkus et al. 2023 (which identifies the standard KGE's compensating bias-and-variability pathology as a real risk for distribution-skewed regimes), Phase 1 onward adopts the following per-objective metrics:

| Objective | Metric | Rationale |
|---|---|---|
| Streamflow (Q) | **KGE_NP** (Pool et al. 2018) | Spearman rank correlation + FDC-based α; robust to glacier-melt heavy tails; avoids the KGE compensating-error pathology highlighted by Cinkus 2023 |
| Baseflow (winter Q) | **KGE_NP** | Same family for consistency; non-parametric α handles the narrow, low-variance winter distribution cleanly |
| Snow (fSCA) | **nRMSE** | Bounded variable; mean-normalized RMSE rescales to KGE-shaped [≤1, →1=perfect] for Tchebycheff compatibility (see §12.4) |

Implementation: `src/calibration_objectives.py` — `KGE_NP` added to the METRICS registry alongside KGE/NSE/LogKGE/nRMSE (commit 35b7dad). All Phase 1 namelists going forward will set `metric: KGE_NP` on Q and baseflow objectives; snow keeps `metric: nRMSE`.

KGE_NP formulation: `1 − sqrt((r_S − 1)² + (α_NP − 1)² + (β − 1)²)` where r_S is Spearman rank correlation and α_NP = `1 − 0.5·Σ|sorted_sim_norm − sorted_obs_norm|` (FDC-based shape distance).

Selection-rule rescaling unchanged: theoretical bounds for KGE-family metrics are `[0, 1]` (clipped) regardless of whether r is Pearson or Spearman, so §12.2's Tchebycheff machinery applies identically to KGE_NP.

**Note on currently running Hunza Pareto**: launched 2026-05-30 with standard KGE on Q and baseflow. We will let it complete and report it as-is; KGE_NP becomes the standard from Chenab Phase 1 onward and the full Phase 1 rollout. If the structural ranking is sensitive to this metric choice, we revisit; the §12.9 selection-rule comparison provides one axis for checking this on the Hunza run.

### 12.9 Three selection rules reported in the paper [PLANNED]

For methodological transparency, the paper will report and compare three Pareto-selection rules applied to the same Pareto fronts:

1. **Theoretical-bounds Tchebycheff** (primary): the "minimize worst-case rescaled shortfall" rule with fixed bounds
2. **Weighted-sum SCEUA** (sanity check): the simpler `w_Q · Q + w_snow · snow + w_baseflow · baseflow` with explicit hydrologic-priority weights
3. **ε-constraint** (alternative): "Maximize Q-KGE subject to snow ≥ threshold AND baseflow ≥ threshold"

This becomes a sub-finding in the paper: how much does the choice of Pareto-selection rule matter for the structural conclusions? — likely answer: less than the structural choice itself, but enough to discuss.
